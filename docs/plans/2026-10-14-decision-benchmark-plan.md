## 1. 公平比较的对象

公平并不要求所有模型使用同一个引擎，也不要求一次 HTTP 请求对应相同次数的 GPU 运算。公平要求相同原始任务池、原文、标签、输出目标、资源边界、失败处理和计时边界；每个模型使用经过验收的正确实现。reranker 后进入精筛的候选可以减少，但最终质量分母不能随之缩小。

同引擎能减少部分工程差异，但不能消除模型参数量、架构、tokenizer、专用算子、并行方式和提示模板的差异。不同引擎的实测延迟可以回答“在这套硬件上实际部署哪个方案更划算”，不能单独证明“某个模型本体天然快多少”。统一 HTTP 字段同样不代表统一推理实现。

当前只执行一个相关片段筛选任务，包含四种链路，分别呈现质量和服务性能。性能表必须同时命名链路、模型与引擎；不制造混合质量、延迟和部署成熟度的总冠军。以下分类行仅为已完成结果的解释边界。

| 报告 | 能回答的问题 | 解释边界 |
| --- | --- | --- |
| 分类质量 | 同题、同标签下，有限选项分类谁更准确 | 不是 产品 的 direct/RAG/Agent 路由准确率 |
| 候选筛选质量 | 同一完整候选池中，谁能选准相关片段并减少漏选 | 是模型与冻结筛选规则的结果，不是生成答案质量 |
| 通用 LLM 参照 | 本地普通大模型在相同分类和相关性任务上的质量和服务延迟 | 使用同一测试机；按实际 GPU 数分组，不与单卡结果混排 |
| 单卡精筛配置性能 | 单卡精筛模型直接与 reranker 前置链路的耗时 | 单列 reranker 资源与耗时，不能把两阶段链路统称单卡总成本 |
| 双卡精筛配置性能 | Qwen3 MoE、27B 等双卡精筛配置的链路耗时 | 披露两个阶段的资源安排；实际端到端与分阶段估算不能混排 |

质量可以跨参数量、跨 GPU 数对照，参数量和资源仍需披露。性能主比较在同一资源组内进行；跨组只讨论效果与资源成本的取舍。

### 3.1 分类场景确认口径（2026-10-15）

按用户最新确认，A 场景只测分类质量与单请求延迟，不做并发负载、吞吐或容量测试，取消此前对话中建议的并发 8 补充。MASSIVE 的 2,974 条记录及 18 类定义保持不变；移除 Intern 后参测为 13 个 Decision 模型和本地 Qwen3 通用 LLM，共 14 个，Qwen3-Reranker-8B 不参加分类。

- 每个模型独占其约定资源，预热后逐题请求，客户端最多一条分类请求在途；一次全量运行同时采集分类结果和时延，不为分位数额外发起请求。
- 质量主指标为 Accuracy、macro-F1、有效输出率；按用户最终简化，延迟主表只保留成功请求平均延迟和 P99。P50/P95 可由原始记录计算，但不放主表；保留全尝试平均时长、失败原因和样本数作为诊断，不报告分类 queries/s 或并发能力。

### 3.2 相关片段筛选四种方式（2026-10-17 纠正）

分类已经完成，当前待测方式严格按用户确认的以下四组，不再用分类或单相关/多相关分层替代。四组都从相同 200 个原始候选池开始，最终输出判定相关的片段集合。

| 编号 | 测试方式 | 完整链路 | 需要回答的问题 |
| --- | --- | --- | --- |
| B1 | Decision 直接筛选 | 原始完整池 -> Decision 逐片段精筛 -> 最终集合 | Decision 不借助 reranker 的质量与耗时 |
| B2 | LLM 直接筛选 | 原始完整池 -> LLM 逐片段精筛 -> 最终集合 | 普通 LLM 的直接精筛基线；与 B1 对照 |
| B3 | reranker 后 Decision 筛选 | 原始完整池 -> 共用 reranker Top N -> 与 B1 相同的 Decision 精筛 -> 最终集合 | 加 reranker 后，减少的工作能否抵消开销，是否增加漏选 |
| B4 | reranker 后 LLM 筛选 | 原始完整池 -> 共用 reranker Top N -> 与 B2 相同的 LLM 精筛 -> 最终集合 | 加 reranker 对 LLM 的收益与损失；与 B3 对照 |

B3 对 B1、B4 对 B2 是同一精筛配置的配对比较；B3 与 B4 使用同一 reranker、固定 N=29 和同一份候选保留规则。小写 `n=1` 是精筛 HTTP 并发上限，大写 `N=29` 是前置保留上限，两者不能混用。每池保留 `min(29, 原池候选数)`，最终不要求凑满 29 个。用户另已确认 reranker 每池一个 HTTP 请求，包含 query 与全部原始候选，取得完整分数后才选 Top29；这不是 29 个候选预先送入 reranker，也不是多个池并发。N 与请求粒度已确认，不再列为待选参数；前置实现、精筛阈值和资源/计时仍须通过执行前验收。

单相关池 9 个、多相关池 191 个（13 个含两个正例、178 个至少三个）、1,438 个相关及 1,756 个无关候选，都是上述四组共用数据的诊断分层，不是新的测试方式。模型/引擎、调用模式、资源也是配置维度；本轮不设置 Qwen3.8 思考对照。各链路各执行预声明的一轮，分层统计不额外推理；单相关 9 池仅作小样本诊断，不单独宣称冠军。标签只用于评分/独立验证集校准，不进模型输入，不按正式子集调整阈值。

**同一场景内的工程覆盖**：完整短/中/长输入、9 到 49 个候选的实际池规模、完整输入边界与超时/非法输出。长度和池规模只解释结果，不另造题、不截断、不填充到统一长度；若报告分层，切分点与成员清单必须根据输入元数据在正式推理前登记，不能看成绩后挑分组。输入拒绝与错误输出属于可用性/接口验收，不属于第三个质量任务。

**明确未覆盖**：现有 200 池没有全无关池，也没有专门标注的词面相似难负例、矛盾证据、跨片段推理或最终答案正确性。不得由“能排除部分无关片段”推断“整池没有证据时可靠返回空集”，也不得把数据中的错误自行改标为新难例。全无关池拒绝是有价值的后续场景，但需要另行确认独立数据、标签及指标，不能静默删除现有池正例、换题或混入本轮分母。

本轮不新增整池一次输入让模型联合挑选、多轮对话/工具路由或端到端 RAG 回答，也不把 reranker 的 Top N 排序直接当作最终精筛结果。前置 Top N 是 B3/B4 的必要步骤，不是被排除的测试方式；最终仍判断零个、一个或多个相关片段。现有证据不变。

- 12 个工程池共 226 对，其中存在 15,458 字符的 query-document。容量工作负载预先限定为 query 加完整片段不超过 2,000 字符的全部 199 对，不截断、不按模型结果择题；长度界限只是选样条件，不代替原生 tokenizer/服务完整输入检查。保存排除清单、长度分布及数据哈希。该预检不能外推到超长片段、完整正式池或线上开放到达流量。
- 每个 HTTP 请求只判断一个 query-document，最多 n 条在途，完成即补充，除启动/收尾外保持负载，不在工程池边界等待。模型只读取问题和本片段，不读标签、其他片段、reranker 分数或名次。
- 同一模型四档共用一个已验收原生部署，不逐档调整引擎/精度/输出预算。支持调度参数的后端固定 max sequences=32、batched tokens=32768；原生 SDK 等特有限制照实披露。Jeva 的串行参考定位保留，不把 HTTP 接入成功当作 GPU 并行。此为优化适配的实测配置，不宣称已证明全局最优部署。
- Laya 在零测量的预热阶段暴露默认 HTTP admission=16 后，经用户批准，仅容量运行显式设为 32 并重新完成独立预热。官方单线程执行器不变，接入排队不等于跨请求 GPU 合批。旧失败证据保留，新快照/输出只续跑精确未测后缀；禁止重跑任何已有测量文件，已完成配置与全部测量函数保持不变。
- 使用现有 Decision 二元 choice 映射；LLM 容量参照采用已验收的 strict JSON 生成路径，温度 0、非思考 64 总输出 token，Qwen3.8 思考配置保留 xhigh/4096 总输出 token。只判断检索相关性，不要求单段足以回答。输出、请求与响应只保留脱敏元数据、哈希、用量和判断，不打印原文/思考/密钥。正式 B 的评分路径和阈值另行验收，不由容量预检代替。
- 各档预热两轮，每轮 20 条按工程输入长度均匀取样的请求，预热、冷启动/JIT 不计成绩；三轮测量次序固定为 `[1,5,10,20]`、`[20,10,5,1]`、`[5,1,20,10]`。每档每轮相同 199 对，请求总数相同；这是有限的闭环负载，不是最大容量或 SLA 测试。
- 请求时延从构造/发送到响应完整接收并校验，包含服务排队，不包含等候客户端空位；另记整个工作负载 wall time。主看成功请求 mean/P95、相对 n=1 的增幅、有效 requests/s 及倍数，同时保留全尝试延迟、失败/超时/非法输出及样本数。n=1 自身跨轮差异与各档判断变化一并记录，不把天然浮点差异直接解释为准确率下降。20% 延迟增幅仅为讨论建议，未冻结为通过线。
- 保留原有 15 款 Decision/LLM、Qwen3.8 两种配置分别记录；不恢复排除模型，不下载/清理权重，不接产品。复用已验收 launcher 和 native mapping，以现有 runner 的独立子命令执行；新目录、新源码快照、共享 classification.lock、零隐藏重试/回退/截断。启动/单请求上限分别 2400/300 秒。超时则停止该测量序列定位，避免残留 GPU 请求污染下一档；已产生的请求不重跑。最后保留 Qwen 服务。

本轮容量预检已完成，结果不改变上述冻结方法，也不自动决定正式筛选并发：部分配置 n20 吞吐接近 n1，而请求延迟明显增长；D3-edge 存在跨轮波动，部分模型在相同输入下的判断随并发改变。完整的逐轮分母、失败、模式、token 与保留证据检查见[结果记录](../research/2026-10-16-decision-capacity-preflight.md#最终审计)。没有把 20% 设为追认通过线，没有重跑或自动优化部署。最后 Qwen3.8 思考服务保留；下面的 B n=1 方法来自后续用户确认，不因容量完成而自动执行。

### 正式筛选方法（2026-10-17 确认 n=1）

主目标固定为：**给定用户问题和完整候选池，比较四条链路最终选出的相关片段集合及完整处理成本。** 最终可以返回零个、一个或多个，不要求凑满 Top N 或排序，也不把真实正例数量告诉模型。前置 Top N 是候选裁减，不是最终相关判断。

精筛调用固定为：**每个被提交的 query-document 独立做一次相关性判断，逐候选串行执行，最多一个请求在途。** B1/B2 提交全池，B3/B4 仅提交前置保留集合。每个精筛请求只看到问题和自身片段，不读取其他候选、reranker 分数/名次或标签；“独立”不是统计上错误独立或概率已校准。n=1 是共同负载条件，不是最佳部署效率或纯模型速度证明。

| 方案 | 原生调用方式 | 对外统一结果 |
| --- | --- | --- |
| Qwen3-Reranker-8B（B3/B4 前置） | 一个 HTTP 请求提交 query 与原池全部 documents；内部用官方模板和 yes/no readout 对各 query-document 独立评分，可按已验收的固定 batch 分批计算 | 返回全部候选分数，按固定排序取 Top29；不是将所有正文拼成一条联合判断，也不作为第五组最终精筛 |
| Decision | 每次一个 SystemOne state，只含 query 和一个完整片段，使用同一二元 `choice` 相关性问题；原生 batch 接口只传一个 state。原生 `noul` 仅在语义和正类映射验收后作为接口适配，不假设其与二元 choice 分数相同，不额外开展模式择优 | 每个候选取得自己的相关性输出，用冻结规则得到相关 ID 集合 |
| 通用 LLM 参照 | Qwen3-30B-A3B-Instruct-2507 与 Qwen3.8 非思考配置先验收原生 yes/no 评分路径；若不支持则在正式运行前固定非思考结构化输出。每次一个候选，关闭 SDK 重试；不新增思考配置 | 顺序覆盖该链路要求的精筛候选；披露实际路径及非思考配置 |

各链路按同一冻结原始池顺序执行，不跨池交错请求。B3/B4 每池只发送一次全候选 reranker 请求，完整取得分数，再冻结 Top29 成员并依原始哈希顺序逐片段精筛，避免把排序提示或额外上下文传给精筛器。一个池请求不等于一次 GPU forward；内部批大小、forward 次数、编码量和资源必须记录，不强制 `max_num_seqs=1`，不在正式运行中搜索 batch、静默拆成多次 HTTP 或因失败降 batch 重试。此确认替代此前文档中 reranker 每请求一个片段的限制，精筛仍逐片段 n=1。

此方案避免把其他候选正文重复塞进每个判断，也不让片段之间竞争一个固定数量的名额。Clef 等共享主干的多问题方案和原生批处理可能有自己的计算优势，因此本轮不测试它们不代表其效果差或一定更慢。独立判断也不解决片段间去重、互补证据组合或上下文预算优化，这些不是现有相关性标签能够完整评测的任务。

一次 `choice` 把所有片段作为互斥选项，回答的是“更倾向选哪一个”，概率在候选间竞争；它不直接回答“哪些都相关、该选多少”。本轮不再用该分布取 Top 3、按累计概率凑数量，或把跨组竞争概率拼起来过阈值。候选级二元判断的相关分数也不自动等于校准后的真实概率，阈值必须按第 4.2 节处理。

取消固定 Top-K 比较树、四档 `score` 期望值和全排序消融。本轮串行是新的 n=1 二元相关性基线，不复用旧串行任务的分数或速度。模型内部有多条序列或多个 forward 不自动等于低效；本轮不比较最佳批处理总成本。

### 4.1 完整输入与阶段调用粒度

在推理前用实际 tokenizer 和官方 encoder 计算完整长度，包括 query、正文、ID、指令、schema 和特殊 token，同时检查真实选项数上限。不能只按字符数判断，也不能把 API 的文档数量上限当成模型上下文上限。

判断语义固定，按模型实际支持的原生路径，在预检阶段验收整池 reranker 与单片段精筛调用并冻结：

1. 每条逻辑样本包含同一 query、一个完整片段和相同判断指令。候选 ID 在适配层保留用于回填，不把其他候选、其分数、名次或真实标签放进该样本。问题要求判断检索相关性，不另加“必须单段足够完整回答”的要求。
2. 精筛每次仅提交一个候选，等待其终态并校验后再提交下一个，不在一个精筛 HTTP 请求内藏入多个候选。reranker 则一次提交一个完整原池，按候选独立评分并返回全部分数；先校验全池长度、ID 覆盖和结果完整性，再选择 Top29。两阶段均记录客户端实际在途峰值、请求 ID、输入/请求哈希和调用次数，不跨池或跨阶段重叠。
3. 顺序、提示和运行时选择不使用正式池标签。精筛调用键为 `(链路条件, 精筛阶段, 池, 候选)`，reranker 调用键为 `(链路条件或声明的共享来源, reranker 阶段, 池)`，各最多一次 HTTP 调用，失败不重试；候选级分数记录引用所在整池请求，不能把一池 HTTP 计成多次调用。B3/B4 允许预声明的 Top29 裁减，除此之外不做局部赢家淘汰或因已找到正例而提前停止。不同链路的预声明调用不是失败重试，记录键不能混淆；跨链路复用证据须遵守第 4.3 节。预检核验 ID、覆盖和固定调用配置下的重复差异，不保证温度 0 必然逐位确定。
4. 超长单段、问题数超限、非法 schema、候选覆盖错误、OOM 和超时分别记录；不能把所有 400/422 都当作长度问题反复拆分。主试验没有自动重试、CPU 降级、静默截断或旧模型回退。

四条链路都要对同一完整原始池给出可审计最终去向，但 B3/B4 的精筛器不必再次处理 Top N 外的片段。前置丢弃为算法选择，不是成功完成精筛，也不是接口失败。统一原文、最终目标、n=1 和全链路计时边界；分阶段披露请求数、编码量、服务时间及资源。不能用 B3/B4 剩余候选的单请求延迟代表整链路提速。

SGLang `/v1/score` 是普通模型的评分入口，不是 Decision 专用接口。官方协议对普通 CausalLM 支持通过 `label_token_ids` 读取 `yes/no` 等标签 token 的 logit 或概率，也支持一次请求中的多个 `items`；对 SequenceClassification 模型则读取分类头分数。本轮可以使用其**单片段评分路径**，每次仅一个 item，但必须先验收提示模板、标签 token、正类方向和分数提取。它不能直接替代 Decision 的 SystemOne，也不能把任意 Decision checkpoint 当普通生成模型接入。

2026-10-15 按用户提出的原生 `score` 对照建议，将其归入 B 场景，A 场景不追加调用方式。复用同一个本地 Qwen3 权重，优先验证 SGLang 原生 CausalLM 标签概率路径；2026-10-17 的 n=1 决定要求每次只有一个 `item`，不开展引擎速度择优。保持每个 query-document 独立、同一完整候选池和计时范围，不开启改变注意力语义的多候选融合模式。分数是在 yes/no 标签之间归一化的相关性信号，不是经过校准的真实正确概率；同样需要独立验证集阈值。路径因兼容性未通过时，保留验收失败证据，在阈值采集前冻结已验收的结构化输出；不在正式运行期间回退。

vLLM 0.31.0 的 `/score`/`/v1/score` 属于 pooling/scoring 接口，支持 cross-encoder、late-interaction 和 bi-encoder。普通 CausalLM 需要兼容的转换和标签读出，并非把现有聊天服务的 URL 换成 `/score` 即可；不能使用随机分类头或把 embedding 余弦分数冒充 LLM 的相关性判断。Qwen3-Reranker 保持其已验收的专用 yes/no 读出。vLLM 与 SGLang 是同一基线的可选执行引擎，不当作两个新模型加入完整榜单；当前测试机上的 Qwen MoE+TP=2 score 兼容性仍待验收，不为此打断分类测试。

核对来源：[vLLM 0.31.0 scoring 文档](https://github.com/vllm-project/vllm/blob/v0.31.0/docs/models/pooling_models/scoring.md)、[SGLang 原生 score 实现](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/managers/tokenizer_manager_score_mixin.py)。代码支持证据不等于本机评分精度或速度成绩。

本地普通 LLM score baseline 单独标为“普通 LLM + 实际引擎评分路径”，不与专用 Qwen reranker 或历史托管 Qwen 混为一条结果。如果预检后固定结构化输出，则 schema 只允许候选 ID 与 `relevant: true/false`，并验证整池覆盖及重复/缺失 ID；硬判断不伪造连续置信度。生成路径温度 0、非思考、64 总输出 token，记录模板/关闭思考设置、用量与停止原因；本轮不使用 xhigh/4096 的 Qwen3.8 思考配置。历史思考记录保留，不打印思考正文。

### 4.1.1 n=1 执行与计时边界

- **全局单飞**：正式推理请求最多一个在途，禁止阶段重叠执行、池间并行、影子调用和后台验证推理。reranker 的一个请求包含一池全部候选；精筛的一个请求只含一个候选。各阶段驻留资源必须单独验收并登记，不能为两阶段结果暗增 GPU。HTTP 结束不一定代表超时后的 GPU 工作结束，须按第 6 节处理。
- **服务保持原生**：沿用已验收的服务、权重、精度、资源和内部调度，不为 n=1 重写 forward 或关闭原生 graph。精筛原生列表的 state/item 数为 1，reranker documents 数等于原池候选数；reranker 内部独立评分的固定 batch 另行登记，不能与 HTTP 并发或 Top29 混称。请求限流与 GPU 内部序列数分别记录。
- **整链路主计时**：从开始原始池任务准备，到完成最终集合校验；B3/B4 包含全池 reranker 评分、Top N 选择/映射、精筛和合并，B1/B2 包含直接全池精筛。记录真实 wall time，不以单条均值乘候选数或均值/P95 相加冒充。阶段时间用于解释主时间。
- **单请求诊断计时**：从开始构造请求到响应及合法性校验结束，包含模板/序列化、网络、服务排队、推理、解析/ID 映射；成功和失败都记录。reranker 请求时延单位是一池，精筛请求时延单位是一个片段，二者不能放进同一个“单片段时延”排名。运行前独立装载/预热不计，整链路内部发生的切换/等待不能静默扣除。
- **n=1 优化基线**：从本轮同一批记录汇总有效请求 mean/P95/P99、有效/已尝试请求数、失败/超时数和全尝试平均耗时，单独列入表四，不另发计时请求。精筛主看 mean/P99，整池 reranker 主看 mean/P95，另一分位数也保留。有效只要求协议合法，不按判断是否正确筛选。直接精筛的完整 3,194 对作为各精筛配置的全量基线，Top29 子集另列，不能混合输入分布；reranker 基线是相同 200 个整池请求及固定内部调度配置。冻结输入 ID/顺序/完整长度/哈希、提示、模型/路径/精度、资源、缓存/预热状态和生成预算。后续并发或部署优化另行授权，在同一工作负载和明确的配置变化下比较请求时延、有效吞吐、失败率及判断一致性；n=1 时延不能外推最大并发或按并发数线性推算吞吐。

两阶段链路不能未经资源验收就声称获得真实在线端到端时延。用户已指定双机在线拓扑：runner 留在测试机，reranker 驻留代理机，精筛驻留测试机；B3/B4 真实顺序请求两端，计入跨机网络、传输、鉴权及客户端开销，不并行重叠阶段。B1/B2 与对应 B3/B4 保持同一测试机精筛资源和配置，报告明确额外的代理机 GPU/显存/CPU 与网络路径，不称为等总资源比较。代理机尚未核实前不假定已可用。若实际只能离线消费前置结果，则仍须标为“分阶段质量评测”，时间最多报告逐池阶段实测合计，不能填进真实端到端列，也不能把已缓存的 reranker 开销记为零。

12 个工程池使用完整 226 对，包括容量预检未测的 27 对长输入；不沿用 2,000 字符筛选条件。先验收单样本长度、整池 reranker 的固定内部调度与显存边界、语义、ID 回填、失败分类和计时边界，再冻结正式路径。当前权威部署复用 `launch_reviewed.py` 的原生 vLLM pooling 与官方 yes/no 读出，按实际 `/rerank` 端点验收；历史 `server.py` 的 128-document 和 batch_size=1/4/8 限制不能替代当前原生服务合同或作为验收通过证据，不回退部署旧 Transformers 服务。旧的“最多 3 组 batch/调度配置择优”不再是本轮前置任务；不进行全模型深度调优。

### 4.2 阈值与选择规则

精筛器的连续相关性分数必须转换成“选/不选”，不能给不同模型随意统一 0.5，也不能只校准其中一类。这里的最终判断阈值不同于前置 reranker 的 Top N；本轮不把 reranker 分数另过相关性阈值来暗中改变前置规则。

- 根据冻结协议中的 32 个 `excluded_historical_pool_ids`，从相同 revision 和文件哈希的 T2 源重建候选及标签，核验与正式 200 池无查询及候选池重复，再按固定哈希划分 12 个工程预检池和 20 个阈值验证池。各模型使用同一验证数据、标签和调参预算。若无法重建或确认隔离，则暂停阈值型正式评测，不能挪用正式 200 池调参。
- 每个模型在冻结 n=1 调用方式后，对同一 20 池只采集一份原生相关性输出。在验证分数形成的阈值切分点中选择池均 F1 最高的全局阈值；同分时依次取池均 Precision 较高、阈值较高者，并记录 `score >= threshold` 的边界规则。阈值搜索包含全选和全不选，不增加模型推理次数；无效输出保留为失败，不通过筛掉失败候选抬高验证分数。
- 若官方接口仅提供硬判断，则冻结其原生判断规则，披露没有连续阈值可调；不伪造置信度。二元 `choice` 或原生接口适配的分数字段/正类方向须先核实，不将互斥候选分布误当成相关分数。
- 同一精筛配置在直接与 reranker 后链路中共用提示、输出映射、最终阈值/硬判断规则、精度、预算、服务配置与 n=1；不为 B3/B4 重新校准一套阈值。不得按正式池正例数量或结果临时改变规则，不在精筛结果上追加隐藏 Top N 限额。

最终比较的是“模型 + 原生调用方式 + 冻结筛选规则”。20 池阈值验证规模有限，且公开正式集已用于前序探索，结论不能外推成未经校准就适用于所有业务。

### 4.3 前置 reranker Top N 与配对合同

本对话此前明确讨论的是 `reranker Top N -> 同一个精筛器`，不是 reranker 单独完成任务，也不是仅排序后把全部候选照常精筛。当前恢复四组对照，不重新假设另一种前置政策。

- B3/B4 共用已验收的 Qwen3-Reranker-8B、权重/模板/精度和排序规则。分数降序，同分按原始冻结哈希顺序；主测试固定 N=29，每池保留 `min(29, 原池候选数)`。无 padding、隐藏阈值或按各池真实正例数量变 N，推理输入不含标签。候选不超过 29 时仍完成全池 reranker 评分并计入开销，不能因没有裁减而省略前置阶段。
- **2026-10-17 用户确认冻结**：固定 Top N=29，替代此前“在 20 验证池上选择 N”的待定方案。已知本对照集每池最多 29 个正例，因此这消除了仅因名额少于正例数量造成的必然漏检，但不保证 reranker 能把所有正例排进前 29。全部 200 池保留，不将高正例数量的池作为特例删除；排序损失按原始标签计入最终 FN。
- N=29 是根据已知数据分布确定的保守主对照，不是验证集最优值、效率最优值或零漏检保证。不同精筛器共用此值，不按正式成绩修改。独立 20 验证池仍用于精筛阈值校准，不再搜索 N；多 N 消融不在本轮执行范围。仅冻结 N 不代表实现、资源/计时验收完成，也不授权立即启动测试。
- 总体结果之外，按原始候选数 `<=29` 与 `>29` 预声明两个诊断分层，报告池数、质量配对差值和工作量/可比耗时。前者没有精筛请求量减少，后者才发生裁减；分层不删除样本、不增加推理，也不替代全 200 池主表。
- 同一原始池的 Top N 成员必须一致并可核验：记录前置分数、排名、保留/丢弃 ID、输入与协议哈希。重复执行前置阶段若得到不同成员，不隐瞒为同一候选集合。
- 资源或预算需要共享一份前置结果时，保存不可变来源和所有消费者引用，不能虚构每条链路都独立执行过 reranker。其质量可按共同 Top N 对照；复用前置/直接精筛记录离线拼出链路时，必须标为派生分析，不算实测整链路延迟，也不冒称新增独立样本。正式执行模式须在验收阶段确定。
- 最终 Precision/Recall/F1 始终对原始完整池标签计算。Top N 外的相关片段若未选中，是最终 FN；不能用保留子集重设 Recall 分母。最终集合必须为原始池子集，且 B3/B4 必须为其 Top N 子集；正确按协议丢弃候选不是接口失败。
- 配对比较：B3-B1 与 B4-B2 分别衡量 reranker 增益/损失；B1-B2 比较直接精筛，B3-B4 比较同一前置下的精筛器。分别报告最终质量差值、精筛请求/文本量减少、reranker 耗时、精筛耗时及可用的整链路耗时，不把某一阶段的改善当整体收益。

## 5. 输入长度、失败与质量口径

所有方案处理相同全文，不统一裁短到某个模型的短上限。实际原生上限、服务启动上限、每序列预算和批次编码量分别记录，不再把曾设置的 2,048/8,192 token 当成厂商模型上限。不同 tokenizer 的 token 数也不是同一个文本单位。

给出两种明确命名的统计，不混称模型能力：

- **全 200 池方案可用性结果**：展示池均 Precision、Recall、F1 和成功率。失败池三项均记零，但状态保留为失败，不能伪装成模型有效返回空集。回答整套方案是否能完成固定任务。
- **共同完整可处理范围的质量诊断**：在推理前根据全文和已验收输入边界确定共同范围，对配对成功池另算质量、披露覆盖比例与失效原因。它是选定子集的诊断，不取代全量表；不得拿各模型各自的成功池分数直接排名。

完整链路成功要求原始候选均有可审计去向、各必需阶段成功且选择规则冻结，最终 ID 无重复、属于原池、无截断。B1/B2 要求全池精筛有效；B3/B4 要求全池 reranker 分数有效、Top N 选择合法、全部保留候选精筛有效。按冻结 Top N 规则丢弃的片段记 `pruned_by_reranker`，不是失败或精筛有效响应；不能因它未被精筛而降低链路成功率，也不能漏算其中正例造成的 FN。前置阶段部分失败不能假装那些候选排名低而继续拼 Top N。

合法最终空集是成功执行，当前每池均有正例，因此 P/R/F1 均为零。任一必需阶段/候选失败则整链路失败，质量按零保留在 200 池分母，不能把部分答案当完整结果。原始评价候选总数固定 3,194，阶段请求数另记：B1/B2 精筛和前置 reranker 覆盖全池，B3/B4 精筛仅覆盖所选 Top N。必需阶段的预检超长项记 `unsupported_length`，不截断或发无效调用；Top N 外无需由精筛器处理的候选不因此判成精筛长度失败。

若因服务故障暂停，尚未执行项标为 `not_run`；某池前置阶段已终态失败，则其精筛标为 `upstream_blocked`、该池链路终态记失败，无须伪造后置请求。不得把这些状态当成已丢弃或合法空集。在所有计划池取得可审计终态前只报告进度，不发布完整 200 池成绩。请求超时后的继续执行条件见第 6 节。

## 6. 部署、配置与测速

运行前冻结一个简洁的部署清单：权重/revision、backbone 和 readout、引擎版本/镜像、精度、原生上限、服务上限、TP/DP、batching profile、调度上限、缓存策略、GPU 数及实际使用 GPU。仅装载 backbone 或将非因果注意力改成普通聊天生成不算同一个模型。

1. **资源**：已有双 A100-PCIE-40GB 测试主机，精筛仍分时独占其约定资源。单卡精筛使用同一 GPU；Qwen3-30B-A3B、Qwen3.8 及其他 TP=2 按实际双卡登记。用户指定 reranker 使用此前代理机的独立部署，不挤占测试机精筛显存；须先验收代理机 GPU/驱动/显存/磁盘、权重/镜像身份和网络路径，不能停止业务服务或擅改驱动来腾资源。配对精筛配置、CPU 配额和客户端位置一致，逐阶段记录显存与采样方法；加 reranker 的额外机器资源单列，不能称为等总算力。分阶段复用结果按第 4.1.1/4.3 节披露，不冒充在线端到端时延；不为本轮另跑 TP/DP 择优。
2. **推理**：保留已验收的官方精度与原生 readout，包括各模型现有 BF16/FP32 差异，不为榜单临时量化或 CPU offload。框架/评分入口适配先用独立题核对模板、决策头、正类方向和数值，不重写 GPU forward。
3. **配置验收**：同一 12 个完整工程池只用于 n=1 语义、长度、单样本路径、重复稳定性及错误边界验收；同一预热和预声明的小子集重复预算，不按质量成绩改提示，不进行 batch 或并发择优。通过后冻结服务身份和调用方式，再使用独立 20 池验证集确定阈值。已知串行限制不阻碍本轮 n=1 质量测试，也不从中推断并行能力。
4. **缓存和预热**：默认关闭可关闭的 prefix/结果缓存；不可关闭则逐项披露缓存键和命中，保证正式请求不是缓存响应。冷启动、JIT、下载和预热均排除。单模型正式执行前预热独立短/长样本直到编译完成，冻结相同的验收停止条件及 2400 秒装载/预热上限；不拿正式最快的一次充当成绩。
5. **性能比较**：模型服务基线为精筛有效单请求 mean/P99（另保留 P95）；方案收益重点为同题配对的实际整链路平均节省时间和加速比，B3/B4 必须计入远程 reranker。完整链路 mean/P95 保留作固定工作负载描述，另附 P99/样本数，不用不同题目的绝对耗时判断模型快慢。成功指协议合法完成，不要求所选集合全部正确；没有真实串联实测时，整链路时延和加速比标未测，阶段合计另列估算。失败同时报告时长、原因和数量。A 的已完成 mean/P99 不变。
6. **不做负载补充**：每个预声明链路条件一轮；四种方式不是并发消融或最快轮次择优。本轮不执行池级并发 4、正式性能重复或首尾正式基线重测。已有容量预检只作独立背景证据；后续原生 batch、吞吐和入围模型优化另立协议，不覆盖本轮成绩。
7. **失败与超时**：保留每个 HTTP 请求 300 秒上限，精筛是一候选请求，reranker 是一整池请求；reranker 内部 batch 不另设可重试调用。取消旧的“整条链路共享 300 秒 deadline”，不将多个精筛请求的串行累积时长超过 300 秒自动判为整池失败。每池记录真实链路 wall time，单次 reranker 请求的超时与整链路累计耗时分开。所有调用零自动重试、回退、截断或预算升级。若请求超时/断连且服务端可能仍在推理，暂停该模型序列，先只读确认取消或完成并恢复空闲；无法确认时不提交下一条，不自动重启/重测。失败记录保留，未执行项明确标记。快速拒绝/OOM 不作为“最快完成”；300 秒不是生产 SLA。

本地 LLM 筛选按第 4 节预检冻结的评分或非思考结构化输出路径执行；模式、温度、输出预算、stop/finish reason 与用量均保留。当前 B 不包含思考配置；score 与生成路径须写全，不能把调用路径或引擎差异当作模型本体的因果优势，也不拼接旧思考成绩作为 B 的对照。

Qwen 的官方模板、yes/no readout 和 pooling 路径继续复用已验收实现。本轮不追加 vLLM/SGLang 性能对照，不实现新的推理引擎或用 LangGraph 重写固定评测循环。Qwen/Vela 专项诊断结果保留，未验收的替代执行路径不直接进入正式基线。

## 7. 指标、必要性与报告口径

A 分类已完成，不重测、不改表。以下只定义 B1-B4 的 n=1 指标，分别从各链路预声明的一轮记录离线计算，不为指标额外发起调用。精筛单请求 mean/P99 是模型优化基线（另保留 P95）；同题整链路耗时差/比值是方案收益比较，必须包含前置开销。整链路绝对 mean/P95 只是固定工作负载的背景描述，并附 P99/样本数，不跨题目推断模型速度；两种统计粒度都保留而不相互替代。

### 7.1 必须展示的主指标

| 指标 | 计算口径 | 必要性与边界 |
| --- | --- | --- |
| 池均 Precision（精确率） | 每池选中的相关数 / 选中总数，再对 200 池等权平均 | 回答“选出来的片段有多少确实相关”；单独看会奖励只选极少数的保守方案 |
| 池均 Recall（召回率） | 每池选中的相关数 / 标注相关总数，再对 200 池等权平均 | 回答“有多少相关片段没有漏掉”；单独看会奖励全选，漏选率就是 1 - Recall，不另列重复指标 |
| 池均 F1（质量主比较指标） | 每池计算 Precision/Recall 的调和平均，再对 200 池平均 | 同时反映误选和漏选；不能替代 Precision/Recall，也不能与延迟加权拼成总分 |
| 完整链路成功率 | 完整合法完成筛选的池数 / 200，显示计数与比例 | 区分“判断错了”和“任务没完成”；必需阶段失败即池失败，合法 Top N 裁减不是失败 |
| 成功整链路平均延迟 | 成功池从原始任务开始到最终集合校验结束的实际 wall time 均值，附池数 | 回答“处理一个问题的全部筛选流程需要多久”；B3/B4 必须包含前置 reranker 与精筛，不只测最后一段 |
| 成功整链路 P95 延迟 | 同一成功池实际端到端耗时分布的 95% 分位数 | 防止均值掩盖较慢任务；200 池规模的混合负载诊断，不是固定长度 SLA；阶段分位数不能相加代替 |

主结果表按同一精筛配置两行相邻排列，展示链路、Precision、Recall、F1（附 95% 区间）、完整链路成功数/200，以及实际整链路 mean/P95。按 Decision/LLM 和实际资源安排分组；没有真实端到端测量则填“未实测”，不能将阶段估算填入这两列。阶段耗时/请求数、两阶段资源和估算放附表。质量与主延迟均按原始池作为统计单位，候选单请求统计单列；每行附质量来源与计时/资源记录引用。不能只展示成功时延而省略失败。模板和配对表见第 7.4 节。

本项目的“找到相关片段的准确性”用以下集合指标表达，不再带 `@K`：令真实相关集合为 R，模型选中集合为 S，TP 为选中的相关数，FP 为误选数，FN 为漏选数。

- **Precision = TP / (TP + FP)**：选出来的有多少确实相关，衡量选得准不准。
- **Recall = TP / (TP + FN)**：所有标注相关片段中找到了多少，衡量有没有漏选；漏选率为 `1 - Recall`，不另设重复主指标。
- **F1 = 2TP / (2TP + FP + FN)**：同时惩罚误选和漏选，作为筛选质量的主要比较指标，同时保留 Precision/Recall 展示取舍。

例如真实相关 5 段，选了 4 段，其中 3 段相关：Precision=75%，Recall=60%，F1 约为 66.7%。只看 Precision 会奖励只选极少数的保守方案，只看 Recall 会奖励全选；候选级 Accuracy 还包含正确排除的负例，不能直接替代“相关片段找得好不好”。

读表时，Precision 高而 Recall 低表示选得少且较准、但漏检多；Recall 高而 Precision 低表示找回较全、但夹带无关片段多；F1 是二者的调和平均，不是算术平均，不能掩盖二者各自的变化。表内 95% 区间描述在当前池级抽样与统计方法下得分的抽样不确定性，不是“95% 的片段判断正确”或单次判断的模型置信度，也不覆盖数据污染、标签偏差及跨业务泛化风险。对同一模型有无 reranker 的优劣，看配对差值的区间，而不是仅凭两条分数区间是否重叠判断；差值区间跨零时，本轮不足以明确区分，不能据此证明等效。

逐池计算后对全部 200 池等权平均，F1 是逐池 F1 的均值，不是汇总 Precision/Recall 再取调和平均。正式池都有正例，合法空集的 Precision 按 0 约定，Recall/F1 也为 0，但完整链路成功仍记 1。失败池三项按 0 计入全量方案可用性，状态仍是失败；不是把没有响应改写成全不相关预测。该约定不自动适用于将来的全负例测试，届时需另定拒绝指标。若无成功完整池，则成功整链路延迟不可计算；若无合法阶段响应，则该阶段成功单请求延迟不可计算，均不填 0。

不把候选拼成大池作为唯一主成绩，避免候选多的题主导结果。平均选中数量用于解释筛选行为，按成功池计算并附成功率，失败不能被当成选择更少的优势。本轮不再把 nDCG、Top 1、Precision@3 或 Recall@3 放入主表，也不为这些旧目标额外调用模型。

### 7.2 必须保留的诊断与证据

这些项目用于解释主指标，不另开推理轮次，不堆入一张排行榜。

| 诊断项 | 口径 | 必要性 |
| --- | --- | --- |
| 分阶段有效率与原池去向 | 请求级 valid / planned：独立全量 reranker 为 200 个整池请求，直接精筛为 3,194 个候选请求，后置精筛为前置成功后选中的候选请求。候选覆盖另记全池 3,194 个及保留、丢弃、失败、未执行状态；复用来源另列 | 合法裁减与漏执行必须区分；不将 3,194 当作 reranker HTTP 请求数，也不能缩小最终 Recall 分母 |
| 失败/超时分布 | HTTP 码、连接/服务超时、OOM、长度拒绝、非法格式/ID/分数、输出预算耗尽等分别计数；超时给出占该阶段计划请求数及已尝试请求数的比例，另记受影响池/候选数 | 区分服务/协议限制与相关性判断错误；合法错误判断不是接口失败，`finish_reason=length` 不能当正常停止 |

| 单请求优化基线与阶段耗时 | 单独列 n=1 有效请求 mean/P95/P99；精筛主看 mean/P99，reranker 整池请求主看 mean/P95。附有效/尝试数、失败/超时数及全尝试均值；直接全量与 Top29 子集分开，另记各阶段与网络开销及复用来源 | 提供后续同负载并发优化基线，解释前置开销；不把请求单位/输入分布变化或缓存命中当模型或整链路提速 |
| 前置正例保留率 | 每池 `Top N 中的正例数 / 原始池正例数`，池均并附计数；前置失败另报状态，不伪造保留集 | 给出进入精筛前已丢失多少正例；该池最终 Recall 不可能超过此上限 |
| 精筛工作量减少 | 每池 `1 - Top N 数 / 原始候选数`，另报进入精筛的字符量/实际 token 量、HTTP 次数与最终选中数 | 确认是否真的少做了工作；不同 tokenizer 的 token 数不能直接跨模型当等量输入 |
| 前置的配对收益 | 同一精筛配置比较 B3-B1、B4-B2 的 P/R/F1 差值、请求量、可比的总耗时差/比值，B3-B4 共用候选集 | 直接回答 reranker 是否值得加入；各阶段 P95 不能相加，资源或计时模式不同不能声称实测加速倍数 |
| 平均选中数量 | 成功池的选中数均值，同时给出这些池的标注相关数均值和成功率 | 解释高 Precision/低 Recall 是偏保守还是误选多；选得少本身不是优点 |
| 共同覆盖诊断 | 推理前冻结共同可完整处理范围，再在配对成功池上报告质量/延迟及覆盖数量；沿用各自冻结阈值，不重新校准 | 区分模型判断差异和部署输入边界；不替代全 200 池表，不按各模型各自成功子集排名 |
| 配对差值 95% 区间 | 质量按完整池簇重采样，同一轮模型共用抽样索引；比较对象在正式运行前声明 | 判断差异是否足以支持结论，不能凭零点几个百分点定胜负；不把区间包含 0 解释成等效 |
| 输入规模与资源身份 | 原文字符数、各自 tokenizer 的完整 token 数、上下文上限；GPU 型号/张数、TP、精度、CPU 配额、引擎/镜像/源码、逐卡显存观测峰值及采样方法 | 解释时延和可部署成本；不同 tokenizer 的 token 数不是相同文本工作量，采样显存峰值不称精确瞬时峰值 |
| LLM 模式与用量 | 实际 score/非思考生成路径、关闭思考设置、输入/总输出 token 的 mean/P95、预算、stop/finish reason 分布；评分接口不适用的输出字段标不适用 | 解释输入/输出长度与服务路径开销，核验未误启思考；不伪造不可得的 token 分项，不把字符数冒充 token，不记录思考正文 |
| 协议完整性 | 链路/阶段/池/候选 ID、数据/请求哈希、阶段单次调用或显式复用、实际在途峰值 1、共同 Top N、无截断/回退/隐藏重试及原证据校验 | 确认四组配对合同；防止把推理复用当独立实测、把合法裁减当接口失败 |

独立执行且输入已确定的每个阶段，以该阶段 HTTP 请求为单位，账目满足 `stage_planned = attempted + preflight_excluded + not_run`、`attempted = valid + failed`；reranker 一池一请求，精筛一候选一请求。B3/B4 在前置成功后另按候选数满足 `原池候选数 = pruned_by_reranker + 后置精筛 stage_planned`。reranker 的候选分数覆盖和整池 HTTP 记录分别保存，任一必需分数缺失或无效则整池前置失败；后置标 `upstream_blocked`、链路记失败，不能把缺失项伪装成低分或假造 Top29。前置/精筛的已复用记录另记 `reused`、来源哈希和消费者，不冒充新调用。预检长度排除与运行时长度失败分列，不重复计数。每次请求尝试的实际 HTTP 调用数为 0 或 1，本地构造失败可能为 0；同一失败的 HTTP 码等是属性，不重复累加。零分母比例记不可计算；尚无链路终态的未执行池只报进度，不冒称完整成绩。

### 7.3 统计与不测项

- 每个预声明链路条件对全 200 池执行一轮，同批响应用于质量、时延和审计；共享前置/派生分析明确标记，不算额外独立轮次。稳定性检查只在工程子集，正式数据不重复取最快值。单轮结果不宣称跨天或生产稳定性。
- 分位数复用既有线性插值：`m` 条耗时排序后位置 `(m - 1) * q`，在相邻值间插值；这里 m 是观测数，不是前置 N。同批请求离线计算 mean/P95/P99。精筛单请求主看 mean/P99，与分类一致；3,194 条全成功时 P99 对应约 32 条尾部观测。整链路和 reranker 的 200 池 P95/P99 约对应 10/2 池尾部观测，因此主展示 mean/P95，附 P99 和实际有效样本数，不据此声称长期尾延迟稳定。P50 可作为附加诊断。
- F1 和配对质量差异使用池级 2,000 次 bootstrap、95% percentile 区间，复用固定随机种子 `public-v3-ci`。候选不独立重采样；若有相同查询/池的重复，整个重复组保持一个簇。Precision/Recall 区间放附表。对公开集的区间只反映该取样口径，不消除训练污染或此前使用正式集的局限，不做多模型穷举显著性“冠军”筛选。
- 不测候选级 Accuracy 作为主成绩：排除大量负例也能很高，不能说明相关片段选得好。不以 nDCG/MRR/Top-K 排序作为最终主榜；B3/B4 仍执行前置 Top N，并报告它的正例保留率，最终目标仍是相关集合。
- 不测 n5/n10/n20、RPS/QPS、最大吞吐、GPU 并行效率或 SLA；n=1 的完成速率不冒称生产容量。已有容量预检单列，不拼接为本轮正式成绩。
- 不新增 TTFT/逐 token 解码速度、分阶段 GPU profiling、引擎/精度/batch 消融；不同原生 readout 不适合用生成速度统一排名。资源和 token 是解释项，不换算未经测量的人民币成本、能耗或综合性价比分。
- 不测最终答案正确性、幻觉、互补证据组合、产品 产品收益或全负例池拒绝能力；当前数据与调用不支持这些结论。没有预声明业务达标线，不把 20% 时延增长或某个 F1 数值事后包装成通过线。

- 阶段性能与资源：每链路/配置的 reranker、选择映射、精筛、合并耗时，HTTP 请求数、候选覆盖、两阶段 GPU/TP/精度、内部 batch 与显存、驻留/切换方式。分阶段逐池成本合计明确标估算，不与实测总时延混排，不把阶段 P95 相加。
- 失败与覆盖：每链路/阶段的 planned、attempted、valid、failed、预检拒绝、not_run、upstream_blocked、reused，附请求单位、HTTP 码、超时、长度、OOM、非法输出及全尝试时长。成功率不能替代失败明细，也不删除失败池。
- 模式与用量：实际评分/非思考生成路径、冻结阈值或硬判断规则、关闭思考配置、输出预算、token 用量与 stop/finish reason；不展示私有原文或思考内容。
- 样本级配对与来源：原池及候选 ID、标签、前置排名/保留状态、最终判断、请求/输入哈希、共享来源及消费者、单次调用和 n=1 证据。所有派生表复用同一轮记录，不为填表重跑推理。

最终结论同时交代质量差值、真实耗时变化、预筛漏检和适用资源/池规模；不设未经确认的加权总分，不因区间包含零就宣称等效，也不将固定 Top29 的结论外推为所有 Top N 的最优结论。

## 8. 从现有代码收敛，不重新造一套测试程序

现有权威 runner 为 `evaluation/runner/scripts/public_decision_benchmark.py`；分类 schema、冻结数据、输入校验和 bootstrap 继续复用。模型服务以官方引擎为准，测试端只保留薄的字段/ID 转换、调用和记录。

执行新协议前需要的窄调整：

1. 复用已有 SystemOne 客户端和单样本适配，B 精筛固定候选请求 n=1、原生 state/item 列表仅含一个候选；reranker 复用整池接口，一个请求的 documents 包含全部原始候选，返回全量分数后取 Top29。分别记录 HTTP 请求与候选覆盖，固定并验收服务内部 batch。实验路径停止使用旧的 listwise 局部 Top 3 淘汰、跨组概率合并或计划中的比较树；错误分类不能对任意 400/413/422 盲目拆分。不改变产品检索行为。
2. runner 明确 B1/B2/B3/B4 链路 ID，输出“原始完整池 + 阶段输入/输出 + Top N 保留/丢弃 + 最终相关 ID 集合 + 原生分数/判断及冻结规则”。复用客户端和字段映射，不另造一套推理服务；区分算法裁减、接口失败、阶段阻塞、未执行和合法空集。
3. 增加独立验证集上的精筛阈值冻结记录及用户确认的共用 N=29 协议记录，不再搜索 N；同一精筛配置跨链路共用阈值。复用集合 TP/FP/FN、原始池分母、ID 校验和 paired bootstrap；补齐前置正例保留率、工作量减少与配对差值。既有 Top-K 排序评分器不能冒充最终集合指标，无需改动产品评分器。
4. 验收各精筛后端单片段二元判断及 reranker 单请求全池独立评分，核验完整输入、候选映射、空集/失败区别和真实在途峰值 1；不需要扩充 `DecisionRequest.questions` 上限，也不以跨请求合批为本轮门槛。添加每请求 300 秒及超时后防止残留工作与下一请求重叠的检查，无重试或自动重启。
5. 增加本地通用 LLM 参照薄适配：两款 LLM 仅按第 4 节验收评分或非思考结构化输出，不新增 Qwen3.8 思考链路；保留用量和模式审计。校验整池覆盖和失败，按实际 GPU 数进入性能分组，不将普通 LLM 包装为 Decision 模型。
6. 将执行清单与产品配置解析解耦：独立 runner 调本地模型服务，不运行产品 worker、调用托管模型、注入私有知识库或启动产品集成流程。
7. 从各链路预声明的一轮记录生成第 7 节指标、阶段分母、失败与配对区间，审计共同 Top N 和复用来源；核验真实端到端计时与分阶段估算的标记，不将它们混排。复用统计工具，不额外重复取优，不把合法错误判断从时延中筛除。分类代码与已完成成绩不变。

分类实现与全部运行审计已完成。B1-B4 的主测试 N=29 已确认；阶段覆盖、Top29 实现、精筛阈值、模型路径、失败/超时、资源安排与链路计时仍待实现或验收。本次只更新方法与执行清单，不修改 runner，不运行推理或切换服务。后续补齐针对性测试与工程池验收，再冻结新协议/源码/部署清单到新目录；不改写 A、容量或专项诊断证据。

1. 分类 15 款模型/16 配置、容量预检与 Qwen/Vela 专项诊断均已完成，保留其结果、局限及全部身份/证据。Intern、D3-27B、Clef-27B 不恢复参测或下载。不在正式测速时传权重或改动运行源码。

3. 各预声明链路条件执行全 200 池一轮，同轮收集质量和阶段/全链路耗时，单独离线审计输入、调用或复用、原始池分母、部署身份及原证据保留。不重跑同一链路阶段已写记录或择优保留；未完成项不冒称完整榜单。
4. 输出 B1/B2/B3/B4 最终质量、同一精筛器有无 reranker 的配对变化、资源与链路时延表、前置召回及工作量诊断。实测与估算分开，单卡/双卡精筛及前置资源清楚登记；不把旧速度、历史托管 LLM、官方数字拼入。A 只保留既有结果入口。后续对入围模型另做部署优化，不回改本轮基线。

公众号采用“Decision 能否帮 RAG 选片段？把中文分类和候选筛选分开实测”的叙事。先解释有限选项决策，再展示新模型、实际部署条件和两项结果；热点来自模型和测试问题，可信度来自固定输入、失败和资源披露。

允许的结论是“在这份公开数据、这些调用和阈值方案、这些资源下，某模型/服务在分类或相关片段集合筛选中表现如何”。不宣称 产品 已提速、不宣称答案准确率提高、不把部署失败算成模型零分，也不把不同引擎速度归为模型本体的因果优势。差值区间不能区分时写“本轮无法明确区分”，不能写成等效或硬选冠军。
