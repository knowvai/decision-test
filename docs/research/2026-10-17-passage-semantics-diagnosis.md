# 片段筛选低 Precision：数据语义与离线诊断

## 结论

**不能把本轮表现归因于“prompt 不要求片段回答问题，所以错了”。已核实，这版 C-MTEB/T2Reranking 的正例包含原始 Level-1：相关、但不能满足信息需求。** 把“至少部分回答”设为必要条件，会排除数据中真实存在的正例，改变任务。

本轮更直接的现象是：模型在当前提示下的分数区分能力有限，而验证集选阈值的目标是 macro F1，不是高 Precision。Clef-flash 保留了 75.04% 的标注负例；其 macro Precision 50.13%，只比全选基线 45.84% 高 4.30 个百分点。它并非完全没有信号，但不宜称为已经具备高精度过滤能力。

提示可以进一步明确标签定义，但尚无控制变量实验能证明 prompt 是主要原因，或改写一定有效。本次没有增加任何推理、修改提示或阈值、重跑测试、变更服务；原正式结果及审计证据不变。

## 数据究竟在测什么

### 原始四级标注

[T2Ranking 原论文](https://arxiv.org/abs/2304.03679)在标注说明中区分：

| 原始等级 | 含义 |
| --- | --- |
| Level-0 | 问题与片段内容完全不匹配 |
| Level-1 | 与问题相关，但不满足该问题的信息需求 |
| Level-2 | 与问题相关，部分满足信息需求 |
| Level-3 | 满足信息需求，准确包含问题答案 |

论文另外明确：**其 retrieval 任务**把 Level-2/3 当相关、Level-0/1 当不相关。这个规则不能不经核对就套用到 C-MTEB 的 reranking 派生数据。

原始分级重排、C-MTEB 二值相关性排序、本轮逐片段二选一集合筛选，是三个不同的评价口径。冻结 C-MTEB 任务代码的主指标为 MAP；本轮是每池等权的 Precision/Recall/F1，不是原官方榜单分数。它也不直接测下游回答正确率、证据充分性或是否能独立作答。

### 对本轮实际版本的回溯

使用冻结版本 `C-MTEB/T2Reranking@76631901a18387f85eaa53e5450019b87ad58ef9`，不是按数据集名称猜测标签定义。

1. 公共源 parquet 的 SHA256 与本轮冻结值完全一致：`ceaf1ba1a4777dbb7aecad86fb8aa9cae7a678af6d711d5529c238e89bb6adff`。
2. 全部 6,129 条 C-MTEB query 均精确对应原始 dev query。6,128 池的正负数量分别与原始 `grade >= 1` / `grade == 0` 完全一致；仅 900 池数量与 `>= 2` 分界一致。**数量吻合本身不等于逐片段映射证明。**
3. 利用公开 T2Retrieval corpus 作为 passage ID 与正文的桥梁，对 query 精确匹配、正文 SHA256 精确匹配后，再查原始 graded qrels，得到以下可直接验证的对应关系。

| C-MTEB 列表 | 原始等级 | 精确匹配的 query-passage 对数 |
| --- | --- | ---: |
| positive | 1 | 70 |
| positive | 2 | 23,308 |
| positive | 3 | 6,136 |
| negative | 0 | 288 |

未发现上述可匹配部分的反向标签或等级歧义。这 70 个 Level-1 正例足以否定“这版数据只把 Level-2/3 当正例”的假设。

证据边界：桥接 corpus 只覆盖原始语料的一部分，尚有 16,037 个 positive 对和 54,161 个 negative 对未取得逐片段原始等级；不能把它们当作映射错误，也不能声称已全量逐片段还原原始标注。此处对数允许同一片段出现在不同 query 下，不能解释为唯一文档数。

唯一数量不匹配的源行是 `source_row=6128`：只有 2 个 positive、没有 negative，原始 qrels 为 15 对。现有 `prepare_t2` 要求正负列表都非空，因此该源行未进入本轮正式或验证数据；本次没有修改或补齐它。

### 本地数据转换没有发现标签错接

直接重读原始 parquet，按本轮 `case_id/source_row` 核对 query、候选正文哈希与 positive 集合：

| 范围 | 池数 | 候选 | 正例 | 负例 | 与公共源对齐 |
| --- | ---: | ---: | ---: | ---: | --- |
| 验证 | 20 | 333 | 116 | 217 | 全部一致，无排除 |
| 正式 | 200 | 3,188 | 1,437 | 1,751 | 全部一致，仅排除已批准的 1 正例、5 负例 |

本地 `public_decision_benchmark.py::prepare_t2` 没有做四级标签二值化，而是直接保留公共源 positive/negative 列表。运行协议、输入文件哈希仍为原冻结值。此前独立审计已核对完整输入、请求哈希、无截断、无重试、所有调用有效；本次投影读取的 requests/chains/threshold 哈希与该审计全部一致。

## 低 Precision 的直接证据

### 相对全选基线，过滤收益有限

以下是全候选直接精筛 B1/B2，无 reranker。P/R/F1 为每池等权的宏平均；FP、FN 为所有候选合计，二者不可混用分母。

| 方法 | macro P % | macro R % | macro F1 % | 平均选中/池 | FP | FN |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 全部选中 | 45.84 | 100.00 | 59.67 | 15.940 | 1,751 | 0 |
| Clef-flash | 50.13 | 93.56 | 62.50 | 13.395 | 1,314 | 72 |
| D3-mini | 50.61 | 93.72 | 62.89 | 13.340 | 1,302 | 71 |
| D3-flash | 50.25 | 96.61 | 63.15 | 13.760 | 1,359 | 44 |
| Qwen3-30B-A3B | 51.25 | 91.59 | 62.90 | 12.825 | 1,224 | 96 |
| Qwen3.8-27B 非思考 | 54.19 | 57.24 | 51.58 | 7.375 | 563 | 525 |

Clef 共保留 2,679/3,188 个候选，其中 1,365 个是正例、1,314 个是负例。它排除了 437 个负例，也误删了 72 个正例。D3-flash 的负例保留率更高，为 77.61%。因此“高 Recall、较弱排除负例能力”是可观察事实，不是仅凭 F1 高低的印象。

Qwen3-30B-A3B 在相同提示下也保留了 69.90% 的负例，问题并非只出现在 Clef。Qwen3.8 更严格，但漏掉 525 个正例，不能把它略高的 Precision 解释为整体更优。分类任务的类别区分能力也不能直接外推到 passage relevance 的细粒度边界识别能力。

置信区间、全部 15 配置及延迟见既有 `2026-10-17-passage-filtering-results.md`。本表不做新的显著排名或等效性判断。

### 阈值优化目标与“高精度过滤”不是一回事

冻结规则：只在 20 个验证池上最大化 macro F1，同分再比较 macro Precision、再选更高阈值，使用 `score >= threshold`。没有设置最低 Precision 约束，也没有按误保留/误删除业务成本优化。Clef 阈值为 `0.11162799104060678`，D3-flash 为 `0.04203846211645464`；这些分数未经过概率校准，数值不能理解为正确概率。

仅用已有**验证集**分数，离线查看固定 0.5 阈值的结果如下。没有修改冻结规则，没有在正式集搜索新阈值：

| 模型 | 验证阈值 | macro P % | macro R % | macro F1 % | 空选择池 |
| --- | --- | ---: | ---: | ---: | ---: |
| Clef-flash | 原冻结值 | 40.61 | 89.58 | 53.71 | 0 |
| Clef-flash | 0.5，诊断用 | 37.72 | 56.86 | 42.53 | 4 |
| D3-flash | 原冻结值 | 41.73 | 97.54 | 56.04 | 0 |
| D3-flash | 0.5，诊断用 | 43.70 | 74.18 | 52.90 | 1 |

本协议空选择池的 Precision 记 0。提高阈值可以减少负例保留，但也会删除正例并产生空池；**宏平均 Precision 不保证随阈值单调上升**。这个诊断不证明不存在更适合业务目标的阈值，也不支持无验证地直接改成 0.5。

验证集仅 20 个独立 query，正例比例与正式集不同：验证全选 macro P 34.68%，正式为 45.84%。这是阈值泛化不确定性，不能把后者更高的分数当作模型能力提升；也不能据此断言小验证集就是主要病因。

### 不是只有阈值问题，分数本身也有重叠

用已有直接精筛分数计算，未生成新预测或调优正式集：

| 模型 | 验证池均 ROC-AUC | 正式池均 ROC-AUC | 正式 pooled ROC-AUC |
| --- | ---: | ---: | ---: |
| Clef-flash | 0.690 | 0.659 | 0.724 |
| D3-mini | 0.729 | 0.686 | 0.740 |
| D3-flash | 0.722 | 0.695 | 0.744 |

Clef 正式正例分数的 P10/P50/P90 为 0.178/0.740/0.901，负例为 0.049/0.319/0.840。存在大量高分负例与低分正例。池均 AUC 衡量同一 query 内正负例的分数排序，pooled AUC 还混入跨 query 比较，不能混为同一指标。

这些数字说明**当前模型、输入与提示组合**的区分能力有限，但不能单独区分“模型能力不足”和“提示未充分激发能力”。AUC 不是正确率，也不是原 C-MTEB MAP。JSON 中额外记录的 sklearn average precision 同样只是本次样本上的描述性诊断，不作为官方榜单成绩。

## Prompt 应如何判断

现行提示位于 `decision_capacity_preflight.py:24`，内容为：

> 判断片段内容与用户问题是否具有检索相关性。只判断相关性，不要求该片段单独完整回答问题。

原生 Decision 适配与 LLM 都沿用这一核心指令；LLM 另外要求严格 JSON。未发现标签方向倒置或适配器悄悄把任务换成“能回答”。

**有证据支持的判断：**“不要求单独完整回答”与 Level-1/2 正例并不冲突。把它删除、改成“必须包含答案”不是一个已经证明正确的修复。Level-1 仍须确有相关性，也不能反过来把“共享词语或泛主题”一律视为正例。

**尚未证实的假设：**目前提示没有展开四级定义与边界，模型可能过度放宽“相关”；明确 rubric 或使用独立开发样本可能有帮助。但本次没有对误例做人工语义裁决，没有做 prompt 对照实验，不能把标注负例中的模型误选自动归为标签错误、数据噪声或某一种语义错误。

## 建议的后续边界（未执行）

1. 先区分产品要“相关片段保留”还是“答案证据筛选”。若要求至少部分满足信息需求，应另设 Level-2/3 标签任务，不能偷偷改当前二值标签后仍声称是同一测试。
2. 若继续比较当前任务，应按已经核实的语义明确正例包含 Level-1，而不是单纯收紧为“能回答”；在独立开发/验证集上做原提示与明确 rubric 的控制变量比较，并人工复核 0/1 边界误例。数据、模型、输入、输出预算及部署保持相同。
3. 把高 Precision 或误保留成本写成预先确定的目标，同时报告 Recall 与空选择率，不能用 F1 最优阈值冒充高精度过滤最优点。
4. 当前正式集已用于诊断；后续若依据这些发现调整提示或阈值，新正式泛化结论应使用新隔离留出集，避免把对旧正式集的适配包装成无偏提升。

本次不执行这些后续实验，不恢复监控、不重启模型或服务。
