# D3 Runtime 参数实测

## 结论与建议

**runtime 确实支持并发合批；但参数调大不等于稳定提速，分类和片段筛选的收益差别很大。**
本轮没有验证出准确率提升，也没有找到适合两模型、两任务的通用新配置。

值得保留的研究候选是原生自动校准，尤其 D3-mini 的分类高并发。下表是本轮两轮合计的
真实结果，**不是已确认的稳态加速**；基线的首轮慢请求也完整保留在分母和延迟中。

| 模型 | 分类并发 | baseline RPS → auto RPS | baseline P95 → auto P95 ms |
| --- | ---: | ---: | ---: |
| D3-mini | 16 | 14.62 → 25.18 | 9062 → 1078 |
| D3-mini | 32 | 29.20 → 38.22 | 2043 → 845 |
| D3-flash | 16 | 22.39 → 23.94 | 933 → 671 |
| D3-flash | 32 | 12.78 → 21.60 | 9949 → 1745 |

auto 实际选出 mini `seq64/tokens5120`、flash `seq64/tokens3072`，不是一味增加预算。
这里的 token 数是合批预算，不是输入截断长度；逐请求 usage 已与完整输入编码核对一致。
但这些格子未满足全部预注册规则：mini n16 的首尾基线 RPS 漂移为 +10.16%；
mini n32 的第二轮增益仅约 1.3%；flash n16 第二轮约 +2.0%，n32 第二轮基本不变。
唯一机械通过规则的是 flash `seq8/n1`：RPS +6.4%、P95 -5.9%。然而 n1 没有触及
seq8 上限，且末尾基线本身比开头快约 3.9%，不能据此认定降低 seq 上限是稳定收益来源；
该配置在 n16 还出现秒级长尾。因此本轮不直接变更生产配置。

**片段筛选：仅调这些参数没有明显的普遍收益，高并发的排队代价很大。**

| 模型 | baseline n1 → n32 RPS | baseline n1 → n32 P95 ms | n32 平均条/批 |
| --- | ---: | ---: | ---: |
| D3-mini | 12.81 → 17.77 | 110 → 2156 | 1.80 |
| D3-flash | 10.50 → 12.16 | 164 → 3279 | 1.55 |

相同并发下，各候选在片段筛选的吞吐增益最高约 4.2%，没有通过预注册筛选。
客户端同时在途 32 个请求，实际并不等于一次算 32 条。建议片段业务先根据延迟预算
限制并发；分类则将 auto 作为下一步冷启动/稳定负载复验对象，而非直接采用某个最好数字。
本轮没有自动启动下一轮实验。

### 长尾与判断变化

- mini 分类 baseline n16 首轮最大请求约 9.24 秒，原生 `compute_ms` 约 9.21 秒；
  flash 分类 baseline n32 首轮最大约 10.19 秒，原生 compute 约 10.11 秒。
  对应请求的原生 queue 约 1 ms。末尾冷部署基线也复现近似长尾，第二轮明显减轻。
  现有证据可定位到原生执行阶段，不能把全部开销精确归为 JIT、图捕获或某个 kernel；
  没有增加 profiler 推理、删除慢请求或用第二轮替换总体。固定预热未能消除后续慢请求，
  也未证明所有执行形状都已充分热身，
  所以本轮不构成完全稳态容量结论。
- 两款模型的分类判断均未变化；flash 的片段判断也未变化。mini 片段在 n16/n32 中，
  **2 个独立输入**相对同部署同轮 n1 出现翻转，共 40 个重复事件，不能称 40 个独立错误样本。
  一个正例的相关概率由约 0.5044 降至 0.4988；另一个负例由约 0.499985 升至约 0.5008。
  原生运行路径标注 `approximate`，观测符合边界概率对批处理数值变化敏感的现象，不是 HTTP 失败。
  这里没有重新调阈值来掩盖变化。mini baseline 的片段样本 Accuracy 从 n1 的 62.50%
  降至 n32 的 61.33%（两轮合并口径），不应宣称 runtime 优化提高了准确率。
- 以上补充诊断逐文件核对首次审计的 SHA256，只读取已有记录，新增推理为 0。
  [补充诊断 JSON](2026-10-19-d3-runtime-diagnostics.json)保留来源文件、行号、概率和长尾定位。

以下为完整协议、全部表格与解释边界。此前质量调优 pilot 的提示/阈值结论仍单独保留，
不与这轮原提示、扩展并发的结果混成一次实验。

这轮专门验证 runtime 参数，不做权重、提示或阈值调优。固定原始 baseline 提示和原生 choice，与上一轮性能测试使用的开发集选定提示不同，不能将两轮绝对 RPS 直接相减。

独立离线审计通过：41,472 次 HTTP 推理调用，432 个块，其中预热 4,608 次、实测 36,864 次，全部 valid/HTTP 200；零失败、超时和未尝试。2,615 个历史文件、50 个冻结源码文件不变。

## 测试口径

- 两款 D3，固定 vllm-srun 0.2.0 / 原生计算、同一张 A100-PCIE-40GB、8 CPU quota、96 GiB 主机内存限制。
- 每任务 128 个冻结输入，来自上一轮性能子集；两轮正反输入/并发顺序。不是新的独立质量样本。
- 每档冷启动后独立预热；基线首尾各测一次，flash 反转七个候选部署的顺序。每个候选只有一次部署。
- n 是客户端同时在途请求上限；max-num-seqs 是 GPU forward 行数上限，两者不是同一参数。
- RPS=有效请求数/两轮整块 wall；mean/P95/P99 用合并请求计算，不平均百分位。包含 HTTP、鉴权与服务端排队，不含客户端等空位、装载、校准和预热。闭环短程负载，不是开放流量、长期 SLA 或生产容量。
- 自动模式的启动校准和所有档位的原生启动检查有内部 GPU 工作，单独计入启动成本，不伪称仅有上述 HTTP 推理。
- 不调用 reranker、不动代理机 embedding/reranker/proxy；没有新增 GPU/CPU、缓存或降低精度。

## 预注册候选规则

同一任务、同一 n，两轮吞吐均至少提高 5%，合并 P95 不超过基线 110%，零失败、零决策变化，且首尾基线吞吐漂移不超过 10%，才标为“候选”。这只是待复验候选，不是生产推荐。
